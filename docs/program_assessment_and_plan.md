# 项目现状评估与路线规划（2026-10-30）

面向：算法创新点定稿 + 论文级对比。主线约束：**LLM + 进化算法（EA）解决矩形覆盖多机器人任务分配与调度问题**。

本文只写可复核的事实与由此推出的判断。每条判断都标注证据来源（实验编号/文件/实测数字）；没有证据的地方标注 `UNVERIFIED`。

## §0 一页结论

1. 项目的方法链本身是完整、可复现、有纪律的：精确 Route-DP 内层评价 + ALNS 宿主 + LLM 离线算子演化 + 冻结/部署/对比流水线，测试 341 全绿。
2. **但部署侧存在一个决定性的测量缺陷**：在与基线相同的墙钟预算下，我们自己的 `Proposed` 臂每轮迭代几乎全花在「生成算子的执行边界」上，10 s 预算只跑出 **63 次迭代**，而 B1 跑出 **8054 次**（差 128 倍），DP 调用只有 1.67 万次 vs B1 的 235 万次。
3. 因此 E19「部署后增益 +0.077%、不显著」这个结论**不能作为「DP 证据演化无效」的证据**——它测的是一个被自身执行开销废掉的方法。这是当前最需要修的一件事，而且它**恰好构成本文最诚实、也最有辨识度的贡献起点**。
4. 三条候选路线里，我推荐 **路线 A：先把执行开销修好，再用「成本感知的 LLM+EA」立论**，而不是继续在算子池替换或离线轮次上加码。
5. 决定「能否写成一篇好论文」的关键数据在 42 单元对比里，正在跑（80/252）。跑完后按 §9 的决策规则走。

## §2 刚发现的决定性事实：预算几乎全花在「执行边界」上

### §2.1 数据（同一实例 `development/BASE/R2_T10_0`，seed 0，10 s 预算）

| 方法 | 迭代/周期数 | 运行时长 | DP 调用次数 | 每迭代 DP 调用 |
| --- | ---: | ---: | ---: | ---: |
| B1（纯 ALNS） | **8054** | 10.000 s | 2,352,668 | 292 |
| CDABC | 4179 | 10.000 s | 1,077,971 | 258 |
| RNSGA | 321 | 10.000 s | 2,088,092 | 6505 |
| **Proposed（我们）** | **63** | 10.179 s | **16,710** | 265 |

### §2.2 推理链

1. 我们的每迭代 DP 调用数（265）与 B1（292）同量级 → **搜索逻辑本身不是瓶颈**。
2. 但每迭代耗时差 128 倍：我们 ≈162 ms/迭代，B1 ≈1.2 ms/迭代。
3. 162 ms 里，265 次 DP 调用按实测 `evaluate_route` 约 5 µs（缓存命中）到 106 µs（10 任务冷）算，只占 **1–2 ms**。
4. 剩余 ~160 ms 来自生成算子的执行路径：`heuristics/alns_solver.py:769-789` 的 `_execute_external` → `CandidateProxy.execute` → `llm/operator_evolution/candidate_execution.py:71-96` 的 `execute_candidate_process`，**每次调用 `multiprocessing.get_context("spawn")` 新建进程并重新 import 候选模块**，另有 `import_timeout_s=1.0`。
5. 推算：每 4 次迭代有 1 次命中 AUX 槽（4 槽 roulette）→ 每次生成调用约 640 ms，其中几乎全是进程 spawn + import。
6. 结论：**在 10 s 预算下，我们的方法只做了 63 次搜索决策；25 段的权重自适应（segment_length=20）连 3 段都跑不满，SA 温度还没降几度就结束了。** 这不是「算子质量不够」，这是「方法被自己的工程边界废掉了」。

### §2.3 为什么以前没暴露

E5/E7 的候选评价是**离线小规模测试台**（`candidate_timeout_ms=2000`、`evaluation_trials=8`、短预算），在那里生成算子的 0.5 s/次开销被摊在「只调 8 次」的测量里，看起来只是慢一点；而部署到「每实例 task_count 秒、要跑上万次迭代」的真实搜索里，同样的开销直接吞掉 99% 预算。**E17 测的是候选质量，E19 测的是部署效果，两者之间那道 128 倍的执行开销鸿沟，就是 F7→F8 断裂的机制解释。**

### §6.1 我为什么不同意「加演化轮次」

用户提过「应该有一个合理的生成算子轮次数」。我的反对理由不变且有数据支撑：

1. **轮次是宣称类型的开关**：一旦主张多轮演化 + 精英 + 父子链接，就从「一次性证据驱动设计」滑到「演化算法」，直接和 EoH/ReEvo/LLaMEA 的主场对撞，而我们的增量（A2 证据）在这个赛道里不构成优势。
2. **当前瓶颈不在轮次**：F7 显示单轮候选质量已经有 +0.207 的中位，F8 显示部署无增益；而 §2 显示部署时方法只跑了 63 步。**在 63 步的搜索里，加多少轮子代都没用——子代根本得不到足够的使用次数。**
3. 正确的位置是把「预算」写进适应度（路线 A 的 ②③），而不是把「轮数」写进宣称。

## §7 推荐路线与论文故事（草案）

**一句话贡献**：在一个内层评价昂贵、外层迭代密集的任务分配问题上，LLM 设计的搜索算子只有在「执行成本被摊平」和「适应度按等预算边际贡献计量」两件事同时成立时才有正收益；我们给出这两个机制，并证明它们能把「有证据的算子演化」转化为可测量的部署增益。

**三层贡献**：
1. **问题结构层**（本文特色，不可替代）：矩形覆盖任务的 8 状态耦合使内层评价必须精确；精确性带来可解释的结构证据（状态后悔、mode gap、成本三分解），但也带来高评价成本 → 这是 LLM+EA 在此问题上必须面对的独特约束。
2. **机制层**（主贡献）：成本感知的算子演化——常驻执行器 + 预算折价适应度 + 配对边际贡献 + null 分布门槛。可检验、可复现、可被否证。
3. **实证层**：42 单元 × 6 尺度 × 多 seed 的跨尺度对比，对 CDABC/RNSGA/MRHDABC/SGA-TS/B1 的配对增益与置信区间。
