# 算子经济学：执行器修复、成本异质性与下一步创新设计

日期：2026-10-30（E21）。作者备注：本文只记录**已实测**的数字与据此做出的设计判断；未验证的部分明确标注 UNVERIFIED。

## 0. 结论先行

1. **42 单元对比被中止**。原因不是时间不够，而是 Proposed 臂仍在用"每次调用新起一个子进程"的执行器：同实例 10 s 预算下它只跑到 41–77 次迭代，而 B1 能跑到 1756 次。用它去和基线比，比的是执行开销而不是算法。
2. **执行器已修好并接进生产路径**：`Proposed` 现在支持 `--proposed-executor warm`（每个算子在一个求解内只起一次常驻 worker）。同预算下迭代数提升 **2.7–54 倍**，makespan 中位改善 **+1.68%**（6 个配对，3 胜 1 负 2 平）。
3. **修好之后暴露了真正的创新空间**：算子池的**单次调用成本跨度约 1000 倍**（destroy 0.01–10.35 ms，repair 8.35–57.8 ms），而现在的两处"记账"都按**每次调用**计，不按**每秒**计：
   - ALNS 的 roulette 选择：等概率对待 0.01 ms 与 10 ms 的算子；
   - 演化适应度（E17）：按"平均单次改进"排名，完全不看成本。
   在固定墙钟预算下，这两处都在系统性地把时间投给"每次看起来好、但每秒很差"的算子。
4. **下一步创新**（第 5 节）：把"每单位时间的收益"变成一等公民——**时间归一适应度 + 成本感知算子选择 + 成本画像反馈**。这不是换故事，而是从我们自己测出来的失败模式里长出来的机制，而且有明确的证伪实验（同质算子池上必须表现为空操作，这正是 E16 的教训）。

## 1. 执行器修复：证据

### 1.1 单次调用成本（40 任务 / 4 机器人 / E7 AUX repair，n=12）

| 模式 | 每次调用 | 相对本地调用 |
| --- | ---: | ---: |
| `original`（每次 spawn 子进程） | **225.19 ms** | 39.4x |
| `warm`（常驻 worker，每次仍做 hash/AST/超时/契约检查） | **8.52 ms** | 1.5x |
| 本地直接调用（同一模块，无进程边界） | 5.71 ms | 1.0x |

结论：开销几乎全在"每调用一次就 spawn + 重新 import 整个包"；常驻 worker 已经吃掉了 96% 的水分，剩下 2.8 ms 是进程边界 + 每次重新校验/重建模块命名空间的代价（这是有意的隔离语义，暂不放弃）。

### 1.3 与既有 E13 数据一致

`outputs/e13_evaluation_efficiency/`（4 实例 × 2 seeds）已经跑过同一条 warm 路径：迭代 92.6 → **703.1**，makespan 3275.96 → **3234.35**（+1.37%），且 nominal 上优于四个 `-exact` 基线。E12/E18/E19 从未使用这条路径——所以 E11/E19 的部署结论不是"方法无效"，是"被执行开销挡住"。

### 1.4 修改落点（已通过 348 个测试）

- `experiments/e6_pair_selection.py`：新增 `EXECUTORS`、`_registered_proxy()`、`close_extra_executors()`；`make_solver(..., executor=)`。

## 2. 修好之后：一次迭代的钱花在哪

`BOTTLENECK/R4_T40_0`，10 s 预算：

| 阶段 | original（56 迭代，183.0 ms/迭代） | warm（151 迭代，66.3 ms/迭代） |
| --- | ---: | ---: |
| destroy 执行 | 74.78 ms（40.9%） | 2.71 ms（4.1%） |
| partial 评估 | 0.13 ms | 0.16 ms |
| repair 执行 | 100.40 ms（54.9%） | **35.36 ms（53.3%）** |
| local search | 7.60 ms（4.2%） | **27.98 ms（42.2%）** |

两件事：调用开销消失后，**生成算子自身的计算（repair 35 ms）和 ALNS 内置的 local search（28 ms）成为全部成本**；而 repair 的 35 ms 已经是"算法的一部分"——它在用精确 DP 为每个插入位定价，这是本方法精确性的来源，不能简单砍掉，只能"值不值得"地取舍。

### 3.3 读出来三件事

1. **成本跨度**：destroy 从 0.01 ms 到 10.35 ms（≈1000x），repair 从 8.35 ms 到 57.82 ms（≈7x）。roulette 对它们一视同仁。
2. **排序会翻转**：`e5_llm_destroy` 是"每次调用收益最高"的 destroy（1927 vs 884），但单位时间收益比 `bottleneck_route_destroy` 低 **268 倍**。也就是说，按"每次调用"评价生成算子，会系统性地偏爱昂贵算子；在固定墙钟下这是错配。
3. **"贵"往往来自精确 DP**：repair 里最贵的是 `regret_k_insertion`（57.8 ms）——它对每个候选插入位都跑一次 Route-DP。这正是本方法精确性的来源，也说明成本不是 bug 而是**可调的设计维度**：同一个算子可以用更低频的 DP 定价换取更多迭代。

注意（限制）：这里的 `gain` 是按"该迭代是否刷新全局最优"归因，destroy 与 repair 共担一次迭代的功劳，因此**不是因果分解**，只能用来看"量级与排序差异"，不能用来宣称某个算子更好。

## 4. 为什么现在的两处记账都是错的（在此问题上）

| 位置 | 现在的做法 | 在固定墙钟下的后果 |
| --- | --- | --- |
| ALNS roulette（`heuristics/alns_solver.py` 分段权重） | 权重只由奖励累计（8/3/1）得到，与耗时无关 | 25% 概率分给 10 ms 算子，等于每 4 次迭代就交出 40 ms 给"最贵的那一个" |
| E17 演化适应度 | `avg_relative_improvement`（每次调用的平均相对改进） | 选出"每次最好"的算子，部署后可能比"每次差一点但快 5 倍"的算子在同预算下更差 |

E16 的教训必须写进来：当时给奖励乘以成本折价因子，结论是**无差异**。复盘原因不是"成本不重要"，而是 **B1 池里所有算子都是 0.01–0.08 ms，成本几乎同质**——同质时成本折价退化成常数缩放，按构造就是空操作。**成本感知只有在成本异质时才有信号**，而现在的池（手工 + LLM 生成）异质性是 1000 倍。这条差异必须作为预注册的证伪实验：同质池上必须无差异，异质池上必须有差异。

## 5. 创新设计 v2：时间预算下的算子经济学（UNVERIFIED 部分见标注）

### 5.1 一句话主张

> 在固定墙钟预算下，LLM 设计的算子必须"按秒计价"：演化适应度、选择概率与反馈信号统一到**单位时间收益**，使 LLM 学会设计**便宜而有效**的算子，并使 ALNS 把时间投给当前最划算的算子。

### 5.2 三个机制

- **M1 时间归一适应度（演化侧）**：候选评分从 `E[ΔM]/次` 改为 `E[ΔM] × 接受率 / 实测单次耗时`。副产品：候选评价本身也要记账（每次调用的秒数与 DP 调用数）。
- **M2 成本感知算子选择（搜索侧）**：分段权重更新时用 `weight ∝ (奖励累计) / (该算子实测平均耗时的归一化)`，或直接以"每秒奖励"做信用分配。
- **M3 成本画像反馈（LLM 侧）**：把每个算子的耗时分解（DP 调用数、O(n²) 热点、每次调用的插入候选数）作为证据喂给 LLM，让"更便宜"成为可设计的指令，而不是碰运气。

### 5.3 预注册假设与证伪设计

| 编号 | 假设 | 证伪条件 |
| --- | --- | --- |
| H-E1 | M2 在**异质池**上优于等概率 roulette（同实例同预算配对，中位 ≥ +1%） | 中位 ≤ 0 或 CI 下界 ≤ 0 |
| H-E2 | M2 在**同质池**（B1-only，E16 设置）上无差异 | 若出现显著差异，说明 M2 的效果来自别的东西（实现噪声/副作用），机制不成立 |
| H-E3 | M1/M3 选出的算子部署后优于 M0 选出的算子（同预算） | 部署差 ≤ 0 |
| H-E4 | M1/M3 使候选的**单次成本显著下降**（中位 −30%）且质量不降 | 成本不降，或质量显著下降 |

### 5.4 消融臂

| 臂 | 执行器 | 选择 | 适应度/反馈 |
| --- | --- | --- | --- |
| A0 | warm | 等概率 | 每次调用质量（现状） |
| A1 | warm | 成本感知 | 每次调用质量 |
| A2 | warm | 等概率 | 每秒质量 + 成本画像 |
| A3 | warm | 成本感知 | 每秒质量 + 成本画像 |

### 5.5 顺序与成本

1. **M2 先做**（只改 `alns_solver.py` + 测试，约 1–2 h），跑 6 实例 × 2 seeds 快速 A/B（≈10 min）：若无差异，立刻停，回到"执行器修复 + 诚实报告"。
2. M2 有差异再做 M1/M3（`llm/operator_evolution/` + `feedback_builder` + `prompt_builder`，约 3–4 h），跑一次 E17 式对照（6 次真 LLM 调用，≈25 min）。
3. 最后才跑论文表：42 单元 × 3 seeds × 6 方法 ≈ 21.7 h，用**最终确定的那套配置**跑一次，避免重复烧机时。

### 5.6 文献定位（UNVERIFIED）

"成本感知的自适应算子选择"在 ALNS/超启发式文献里有先例（例如带时间预算的算子选择、以及以"每次迭代收益"为奖励的 AOS 变体），**本文档尚未做定向核查**，必须先查再写进论文。可辩护的差异点应当是：

1. 时间归一的对象是 **LLM 离线设计的算子**，而不是人工算子的超启发式池；
2. 成本信号**回流进 LLM 的反馈**（M3），即"算子必须按秒计价"进入生成目标，而不只是选择层的工程技巧；
3. 成本异质性的来源是本问题的**精确 Route-DP 内层定价**——这是问题结构带来的，不是人为加入的。
